# S0.1E — Multiplayer Server Administration Dashboard

The lobby server includes an **opt-in, localhost-only** operator console at
`http://127.0.0.1:8080/admin/`. It uses the existing ra2lobbyd process; no
additional services, database, reverse proxy or player account system.

## Capabilities

- Live summary of total, started, waiting and private rooms and connected
  *room participations* (not unique account totals).
- View public **and private** room records, host and guest display names,
  platform tags, map, room age, and reported/connected occupancy.
- View V3 registered endpoints, forwarded/dropped datagrams, relayed bytes,
  cumulative control connections, joins/failures and port relay usage.
- Filter the directory to waiting, started, or private rooms; refresh on
  demand or automatically every ten seconds while the tab is visible.
- Close a **waiting** room after confirmation: delete its lobby record,
  release its allocated relays and notify the host and connected guests.
- **Started rooms are read-only.** Removing a directory record cannot
  terminate an already-running player-hosted deterministic simulation.
- Settings and history are not persisted. This is a live operations view,
  not an account management or anti-cheat interface.

## Security design

1. The HTTP operator listener is bound to loopback only (default:
   `127.0.0.1:8080`). Configuration that would bind to a public or
   wildcard interface is refused at startup.
2. The console/API is enabled only when `RA2_ADMIN_TOKEN` is set to a
   high-entropy secret **at least 32 bytes long**. Leave it unset to
   disable the dashboard while preserving local `/healthz` and `/metrics`.
3. Every API request supplies `Authorization: Bearer <token>` in the
   header. The token is compared using SHA-256 and a constant-time digest
   comparison. The HTML/JS never embeds it.
4. The browser keeps the token only in the running page's JavaScript
   memory; it does not use cookies, URL parameters, localStorage or
   sessionStorage. Reloading the page requires the token again.
5. Dashboard responses use `Cache-Control: no-store`, a restrictive
   Content Security Policy, `nosniff`, no frames and no external scripts.
6. Mutating calls are POST-only, require a bearer token, validate the
   request Origin when present, and reject request bodies.
7. The API lists display names and platforms but does not reveal IP
   addresses, player IDs, tunnel IDs, passwords or socket details.
8. Do not expose or forward the operator console publicly. For remote
   administration, connect through an SSH tunnel instead of opening 8080
   in the server firewall.

The bearer-token model protects this loopback dashboard from untrusted
remote browser requests. It is not a replacement for transport-layer
security or workstation security. An operator token visible to local
malware or copied into an untrusted environment is compromised and should
be rotated. No user registration, SSO, or audit-log persistence is
implemented in this slice.

## Start locally

Build the Go daemon with Go 1.22+:

```sh
cd server
go test ./...
go test -race ./...
go build -o ra2lobbyd ./cmd/ra2lobbyd
```

Generate a new secret locally and keep it private. For example, in Bash:

```sh
export RA2_ADMIN_TOKEN="$(openssl rand -hex 32)"
./ra2lobbyd --listen 127.0.0.1:50000 --v3 127.0.0.1:50001 \
  --admin 127.0.0.1:8080 --allow-loopback
```

Visit **http://127.0.0.1:8080/admin/** on the same computer and enter
the token from your local terminal. Do not paste the token into a public
chat, issue, GitHub workflow, build log, URL, or repository file.

From a remote workstation, first create an SSH tunnel:

```sh
ssh -L 8080:127.0.0.1:8080 operator@your-server
```

Then open **http://127.0.0.1:8080/admin/** locally. Keep the remote
server's admin listener bound to 127.0.0.1. SSH port forwarding itself
does not require the dashboard to listen on a public interface.

For future systemd use, store the secret in a permission-restricted
environment file outside the repository. Restarting the daemon currently
resets live rooms and metrics because no state is persisted.

## API (token required)

| Method | Path | Purpose |
|---|---|---|
| GET | `/admin/api/status` | Aggregate room and relay health |
| GET | `/admin/api/rooms` | Operator room roster, private rooms included |
| POST | `/admin/api/rooms/{CODE}/close` | Close waiting room only |
| GET | `/admin/` | Static login shell; contains no privileged data |

Possible close results: `200 closed`, `400 bad_room_code`,
`401 unauthorized`, `403 bad_origin`, `404 room_not_found`, or
`409 started_match_cannot_be_closed`.

Local `/healthz` and `/metrics` are unchanged and still intended only
for trusted localhost monitoring.

## Test and release gate

- `server/internal/admin/admin_test.go`: loopback-only binding,
  explicit high-entropy token, no token disclosure, unauthorized API
  requests, bad Host/remote address, method restrictions and cross-origin
  mutation rejection.
- `server/internal/lobby/admin_test.go`: private room visibility to
  operators, roster privacy, host/guest notifications, resource cleanup,
  reopening a room and refusing started-game closure.
- `.github/workflows/lobby-server.yml`: `go test -count=1 ./...`,
  concurrent socket stress, `go test -race`, `go vet`, and Linux build.

**No VPS changes, public exposure, production configuration or merge into
`master` was performed by S0.1E.** Operators must still test the
dashboard on a disposable loopback server with actual clients before
using room moderation for a public community.
