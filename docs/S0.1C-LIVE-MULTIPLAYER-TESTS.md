# S0.1C — Concurrent live multiplayer verification

## Scope

Option A: a single `ra2lobbyd` instance maintains the central lobby and
CnCNet-compatible V3 UDP relay, while each player-hosted match runs its game
simulation on the clients. No dedicated game simulation was implemented.

## Test matrix

| Test | Current automation | Interpretation |
| --- | --- | --- |
| Four separate 2/4/6/8-player groups | `TestLiveConcurrentV3Matches` | 20 synthetic client control connections and UDP sockets |
| Multiple public room codes | `TestLiveConcurrentV3Matches` | Four independent created/started rooms |
| TCP handshake/version gate | `hello` / `hello_ok` on real loopback sockets | Uses the production control-plane parser |
| Room joining and host notifications | `join` / `joined` / `peer` | Joins directed to the correct room host |
| UDP relay data plane | `tunnel.Serve` on a real localhost UDP socket | Both directions, real V3 packets, every guest against its room's host |
| Datagram integrity | Compare forwarded packet bytes | Preserves headers and payload |
| Unexpected stray delivery | Read all endpoints after traffic | No unrequested traffic observed for cooperative clients |
| Room lifecycle isolation | Close the 4-player room while others remain | Other match hosts stay connected and responsive |
| Capacity and races | Existing `TestConcurrentCreatesRespectServerRoomCap` and `TestConcurrentJoinsCannotOverfillMatch` | Parallel directory operations |
| Guest disconnect and relay cleanup | Existing `TestDisconnectedGuestReleasesTunnelID` / `TestClosingRoomFreesPortRelayWhileGuestStaysConnected` | No stale allocated room slots or relay port |
| Race safety | `go test -race ./...` | CI race detector |

The test intentionally sends player-like payloads and V3 packet headers. It
**does not simulate RA2 gameplay**, inspect synchronization hashes, verify
Android hardware, exercise public Internet NAT traversal, or prove protection
against malicious V3 packet injection. The V3 tunnel is currently a global
ID relay without per-room cryptographic authorization; a malicious client
could address a different registered tunnel ID. Do not describe this test as
a security proof.

## Automated commands

```sh
cd server
go test -count=1 ./...
go test -race -count=1 ./...
go test -count=10 -run '^TestLiveConcurrentV3Matches$' ./internal/lobby
go vet ./...
go build ./cmd/ra2lobbyd
```

`.github/workflows/lobby-server.yml` executes Go tests, race checks, vet
and binary builds on feature-branch pushes and pull requests.

## Remaining real-game acceptance

1. Install authorized RA2 game data on two or more test machines.
2. Build the current engine and server branch with their matching protocol
   versions. Launch the server only on a disposable loopback/test network.
3. Run two independent pairs of actual RA2 client processes, then repeat
   with 4-, 6-, and 8-player sessions. Use distinct room codes and V3 tunnel
   IDs; gather `ra2lobbyd_v3_forwarded_total` and game `net trail` hashes.
4. Verify both clients in each pair agree on session seed/options and run
   3000 game frames with no desync. Existing
   `scripts/play/mp-online-loopback.ps1` and
   `scripts/play/net-match.ps1 -Online` provide single-match starting points.
5. Join from real Windows and Android clients over different networks,
   checking touch controls, matchmaking, NAT traversal and disconnects.
6. Exercise one match closing while the other matches play; check that
   other rooms remain visible, playable, and unaffected.
7. Record measured latency, CPU, resident memory, UDP traffic, and dropped
   datagrams before approving a public VPS rollout.

Do not deploy to a VPS, change firewall settings, or merge into `master`
until the real-game and cross-platform acceptance gates are satisfied.
