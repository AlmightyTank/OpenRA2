# S0.1F — Safe deployment, monitoring and release validation

**Status:** Source implemented on `feature/multiplayer-server-v0.1`. This is
a **deployment-ready toolkit, not an authorized production deployment**.
No code or script in this slice installs a unit, opens the VPS firewall,
changes production DNS, restarts services or deploys automatically.

## 1. What the server actually provides

Option A is a central TCP room directory and UDP relay for **player-hosted**
games. It does **not** host the match simulation, preserve rooms through a
server restart, or restore multiplayer sessions after a host disconnect.
Multiple independent matches may use one lobby/relay instance.

| Endpoint | Default | Exposure |
| --- | --- | --- |
| Control plane, optional V2 HTTP | TCP 50000 | Public **only after authorization** |
| CnCNet V2 transport | UDP 50000 | Public if V2 is enabled |
| CnCNet V3 game relay | UDP 50001 | Public for game traffic |
| Per-client header-less relays | UDP 50100–50999 | Public only if configured/needed |
| Operator dashboard, health, metrics | TCP 127.0.0.1:8080 | **Loopback only**; never expose directly |

These defaults can conflict with other programs. Inspect the actual
target host and existing services before assigning ports; do not blindly
replace an nginx, EpochKick or other production service.

## 2. Candidate build and verification

The branch workflow `.github/workflows/lobby-server.yml` runs:
- `go test -count=1 ./...` including concurrent matches and security tests
- five repeated live-socket match test runs
- `go test -race -count=1 ./...`, `go vet ./...`
- dashboard JavaScript syntax validation
- Go compilation and a real loopback smoke test against `/healthz`,
  `/metrics`, the authenticated dashboard API and disabled unauthorized API
- guarded first-install, staging, normal rollback, and offline rollback tests
  using temporary directories and a fake systemd status command; **never real
  systemctl or a live VPS**
- a real daemon-level TCP/UDP probe (`server/deploy/network-probe.py`):
  connect two test peers, create/join a room, forward packets bidirectionally
  through the V3 relay, then close the test room; loopback only
- static, reproducible Linux amd64 and arm64 candidate binaries using
  `-trimpath -buildvcs=false`, plus `SHA256SUMS`. Uploaded as GitHub Actions
  artifacts with a 14-day retention. These are **not** auto-published releases.

The selected candidate must be the correct CPU architecture for the host.
Copy it and its checksum file privately to the authorized staging machine.
Run:

```sh
sha256sum -c SHA256SUMS
./ra2lobbyd-linux-amd64 --version
./ra2lobbyd-linux-amd64 --check-config
```

The checksum file includes both architectures, so download both files or
extract the selected digest into a single-entry checksum file and use it
with the selected executable. The `release.sh` helper checks the file
contents using the first SHA-256 digest, not its filename. The production
systemd unit performs a second `--check-config` with the configured
environment immediately before starting the actual daemon.

## 3. Security and configuration

Systemd is the preferred production path for a standalone Ubuntu VPS.

- Use the template `server/deploy/ra2lobbyd.service`.
- Copy `server/deploy/ra2lobbyd.env.example` to
  `/etc/openra2-lobby/ra2lobbyd.env` **outside Git**, owned by root,
  mode `0600`. Add a private `RA2_ADMIN_TOKEN` generated locally using
  `openssl rand -hex 32`.
- The dashboard token is optional. Without it, the operator UI is disabled;
  loopback health and metrics remain available.
- Never store the token in the repo, print it to CI logs, add it to an
  unencrypted backup, place it in a URL or expose port 8080.
- The daemon unit uses `DynamicUser=yes`, read-only system protections,
  and executable release files from
  `/opt/openra2-lobby/current/ra2lobbyd`.
- Confirm only one deployment method is active. The optional production
  Compose example is `server/deploy/docker-compose.prod.yml`; its
  `RA2_IMAGE` should be pinned to an immutable digest and it must **not**
  run alongside systemd on the same ports.
- Never enable an automatic external rolling deploy while games are live.

Review the full token and loopback protections in
`docs/S0.1E-ADMIN-DASHBOARD.md`.

## 4. Staging and cutover (operator-initiated only)

**The release helper never starts or stops anything.** It only verifies a
candidate and updates versioned, read-only release symlinks. It has separate
commands for first install and upgrades.

First installation (on an empty, approved dedicated machine, AFTER checking
that the required ports are not occupied and existing services are healthy):

```sh
# Example for a binary and a single-entry checksum, already copied to /tmp.
# The candidate should be renamed ra2lobbyd to match the unit's ExecStart.
sudo env RA2_MAINTENANCE_ACK=YES RA2_BOOTSTRAP_ACK=YES \
  RA2_RELEASE_NAME=v0.1f-rc1 \
  bash server/deploy/release.sh bootstrap \
  /tmp/ra2lobbyd /tmp/RA2-SHA256SUMS --apply
```

The helper refuses bootstrap if a current release, healthy admin endpoint,
or active dedicated `ra2lobbyd` systemd unit already exists. It stages the
candidate but does **not** install or start a unit. Review the unit first
using `systemd-analyze verify`, install it only with explicit approval,
then use `systemctl daemon-reload` and `systemctl start ra2lobbyd`.
Do not run these on a shared VPS without a separately approved rollout.

For an **upgrade** of an already running dedicated lobby:

```sh
sudo bash server/deploy/release.sh preflight /tmp/ra2lobbyd /tmp/RA2-SHA256SUMS

# Only after players have been informed and a maintenance window approved:
sudo env RA2_MAINTENANCE_ACK=YES RA2_RELEASE_NAME=v0.1f-rc2 \
  bash server/deploy/release.sh stage /tmp/ra2lobbyd /tmp/RA2-SHA256SUMS --apply

# Separately, with explicit operator approval:
sudo systemctl restart ra2lobbyd
curl -fsS --max-time 3 http://127.0.0.1:8080/healthz
curl -fsS --max-time 3 http://127.0.0.1:8080/metrics
```

Preflight refuses upgrades if the local health/metrics endpoint is
unreachable, or if **rooms, V3 endpoint mappings, or relay allocations**
are nonzero. Zero counters are still **not proof** that no player-hosted
match is in progress: a match can have disappeared from the directory and
still be playing. The operator must independently confirm the maintenance
window, empty active games, and acceptable player impact.

The rollout is intentionally **not zero downtime**. A restart loses
in-memory room state and interrupts existing UDP mappings and control
sessions; clients must reconnect to new rooms.

## 5. Rollback

After an unhealthy but still responsive release, first confirm that active
games and relay mappings are drained:

```sh
sudo env RA2_MAINTENANCE_ACK=YES \
  bash server/deploy/release.sh rollback --apply
# Separate operator approval to restart:
sudo systemctl restart ra2lobbyd
curl -fsS http://127.0.0.1:8080/healthz
```

If the new binary **cannot start at all**, rollback has a separate
fail-closed offline path. With the affected dedicated service verified
installed and **inactive** by systemd, and a previous release available:

```sh
sudo systemctl status ra2lobbyd
# After confirming no service is running:
sudo env RA2_MAINTENANCE_ACK=YES RA2_EMERGENCY_ACK=YES \
  bash server/deploy/release.sh rollback --apply
# Re-start only after an explicit incident-recovery decision:
sudo systemctl start ra2lobbyd
curl -fsS http://127.0.0.1:8080/healthz
```

The offline path refuses if systemd cannot verify an installed, inactive
service. It does not kill processes, bypass active-service checks, start
services, or claim that a rollback restores in-progress matches. The
previous release binary remains present under `releases/`, and the helper
updates `current`/`previous` symlinks atomically.

If a rollout fails, preserve logs, current release digest, current metrics
and the prior package. Do not repeatedly restart a service while players
remain connected.

## 6. Monitoring and alerts

The localhost-only `/metrics` output includes room activity and
network-control counters, plus V3 forwarded/dropped datagrams, bytes,
registered endpoints, join failures, and relay allocations.

`server/deploy/prometheus-alerts.yml` provides optional examples of:

- lobby scrape failure for more than 2 minutes;
- missing room metrics for more than 3 minutes;
- elevated V3 packet drop ratio (over 10%, with a minimum traffic count);
- repeated failed lobby joins.

These are *sample* thresholds, not demonstrated production baselines.
Configure a local Prometheus scrape job named `openra2-lobby` to target
`127.0.0.1:8080`; do not expose this endpoint on a public interface.
Test thresholds with synthetic load before enabling paging. Report CPU,
RAM, bytes/sec, UDP loss and client RTT separately via host-level metrics.

Suggested operational checks: poll health every minute, review server
errors and UDP drop ratios each day, and inspect capacity before announced
play sessions. Avoid collecting or exporting player IP addresses unnecessarily.

## 7. Release acceptance checklist

- [ ] Go CI including race and smoke test is green at the exact release SHA
- [ ] Candidate SHA-256 and host architecture verified
- [ ] Native C++ engine CI green at the same multiplayer branch
- [ ] Windows and Android binaries from compatible source revisions
- [ ] At least two real Windows ↔ Android sessions with matching 3000-frame
      sync-hash trails and no out-of-sync errors
- [ ] Repeated 2/4/6/8-player real matches, not only synthetic sockets
- [ ] Public Internet/NAT testing, packet loss, latency and network
      transitions measured; documented limit for unauthenticated V3 rebind
- [ ] Dedicated VPS capacity, existing services and ports reviewed
- [ ] Security review for dashboard/token, traffic abuse, DoS/rate limits
- [ ] Operator secret installed only on host and admin bound to loopback
- [ ] Maintenance communications, rollback drill and monitoring validated
- [ ] An explicit merge and production deployment approval obtained

**Blocking:** Current test evidence from S0.1C–S0.1F covers synthetic
network clients, C++/Go tests, loopback server operation and an actual
daemon-level TCP/UDP probe. It does **not** establish production readiness,
cross-platform hardware acceptance, or public Internet NAT correctness.
No approval is assumed.

The `master` branch remains unchanged while this work stays in the
draft multiplayer PR. Never deploy merely because CI builds a candidate.
